## 1. T0.2 真机收尾

### 1.1 实测环境

| 项 | 值 |
|---|---|
| 机型 | OPPO **OPD2601**，Android **16 / API 36**，arm64-v8a（只构建此 ABI） |
| 屏幕 | 2120×3000 @400dpi → **devicePixelRatio 2.5**，横屏 3000×2120 |
| 内存 | **7.76 GB**（验收预算仍按 4GB 保守线） |
| adb 序列号 | `<设备序列号>` |
| GMS | 包存在但 `ro.com.google.clientidbase=android-oppo`（非 Google 认证）→ ML Kit 可用性待 T0.3 |
| 冷启动（极简 spike） | 332 / 359 / 457 ms（预算 2500ms） |

### 1.2 测试方法

- **丢笔**：单页连写 100 笔，比对 HUD 记录笔数与 JSON 中 `points.length < 3` 的笔数。
- **帧成本**：自建 canvas 的 build + raster 分段计时，读 HUD 中位值（非满帧帧率）。
- **压感/采样**：逐点记录 `p` 值与相邻点时间差，统计压感取值分布与采样率中位。
- **掌拒**：开着「非笔输入」开关，掌侧压屏书写，统计段内相邻点跳跃距离的分位数。
- **恢复**：`adb shell am force-stop` 后重启，看是否回填笔画。

### 1.3 六项指标

| 指标 | 通过线 | 实测 | 判定 |
|---|---|---|---|
| 连续书写丢笔数 | 0 | **100 笔 → 记录 100 笔**，点数 <3 的笔 0 个 | ✅ |
| 帧率（中位） | ≥ 55fps | build **3.2ms** + raster **1.1ms** = **4.3ms/帧** | ✅ 远低于 16.7ms 预算 |
| 视觉延迟（中位） | ≤ 30ms | 仅主观「还可以」，**无帧数** | ⚠️ 缺 |
| 单页 3000 笔内存 | ≤ 60MB | 2127 点 → 估算 83KB；**未写到 3000 笔** | ⚠️ 缺 |
| JSON 含压感/时间戳 | 是 | 每点 `x/y/p/t` 齐全 | ✅ |
| 杀进程后恢复 | 完好 | force-stop 后 `已恢复 3 笔` | ✅ |
| 长时书写（10 分钟） | 不退化 | HUD 计时 2:12，但**笔墨时间跨度仅 36.3s**（page0 100 笔 28.3s + page1 3 笔 2.1s） | ❌ 未做 |

**压感与采样（优于预期）**：

- 压感 **0.0–0.877 连续变化**，无一点恰好等于 1.0 → 真手写笔压感，量化 **1/1024**。
- 采样率中位 **187–240 Hz**（随书写速度变化），120Hz 屏足够。
- 掌侧压屏时 **0 段超过 40pt 的跳跃**，段长中位 2.74pt、95 分位 6.3pt → 掌拒在「只收笔」前提下有效。

> **读数陷阱**：HUD 的「抖动率 0.0%–0.9%」不等于满帧。132 秒里只产 1293 帧（≈9.8fps），因为页面静止时不渲染；它只证明「画出来的帧都便宜」，**不能当帧率验收**。曾误判该值可代表帧率，006 未沿用此结论。

### 1.4 本轮修掉的真实缺陷（`22e1f10`）

**现象**：用户开着「非笔输入」书写时，画面上出现一条从笔尖飞向掌心的直线。

**根因**：Flutter `Listener` 收到屏幕上**所有** pointer，第二根手指/手掌的 move 事件被 append 进当前这一笔，同一笔内坐标突变。

**修复**：落笔时记 `_activePointer`，`move/up/cancel` 只受理同一 pointer；HUD 增加「输入」字段显示 `PointerDeviceKind`，让「只收笔」是否生效肉眼可验。

## 2. T0.4 PDF spike

### 2.1 Spike 代码与素材

```text
spikes/pdf_spike/
├─ main.dart            入口：必须先 await pdfrxFlutterInitialize()
├─ pdfrx_source.dart    用 pdfrx 实现 §7 的 PdfSource
└─ pdf_spike_page.dart  七段分段计时 + 日志面板
tool/patch_pdfium_mirror.py   把 pdfium 下载地址改指镜像
```

七段计时：① openFile ② 第 1 页渲染（首屏=①+②）③ 连翻 20 页 ④ 含 PNG 编码的 `renderPage` ⑤ 400% 渲染 ⑥ 文本层片段数与近似字号分布 ⑦ RSS 增量。

素材：真实卷 `paper_math_midterm.pdf`（860KB / 2 页 / A4 595.3×841.9pt），以及 3 页手写 ASCII 冒烟卷、50 页合成卷（132KB）。**合成卷只验证管线，不能代替真实排版**。

### 2.2 构建坑：pdfium 从 GitHub 下载，构建静默卡死

**现象**：`flutter build` 卡在 `assembleProfile` 15 分钟，无输出、不报错、不结束。

**根因**：`pdfrx → pdfium_flutter → pdfium_dart` 的 native assets build hook 从 `github.com/bblanchon/pdfium-binaries/releases/download/chromium%2F7811/pdfium-android-arm64.tgz` 拉 `libpdfium.so`；本机对 github.com 稳定超时（沙箱代理 502），而 hook 里 `getWithRetries` 只对「可重试状态码」重试，超时被反复吞掉。

**修复**：`tool/patch_pdfium_mirror.py` 把 URL 前缀换成 `https://gh-proxy.com/`（实测 HEAD 200、Range 206），幂等，`flutter pub cache repair` 或升级 pdfium_dart 后重跑一次。同时用 `--target-platform android-arm64` 只构建一个 ABI（省掉另两个各 20MB 的 pdfium）。

**校验**：APK 内含 `lib/arm64-v8a/libpdfium.so`（6.4MB）与 `libpdfrx_pdfium_gate.so`，构建耗时 **3m34s**。

> ⚠️ 这是修改 pub-cache 第三方包的应急手段，只在阶段 0 用。产品化（第 1 周 T1.3/T1.5）前必须换成内网镜像或随仓库分发。

## 3. 暴露的契约级问题与拍板

### 3.1 `renderPage` 返回 `Uint8List` 是错的

| 操作 | 耗时 |
|---|---|
| pdfium 渲染一页 | **3–12 ms** |
| 转成 PNG | **120–135 ms** |
| 合计（按现契约） | 120–138 ms |

**根因**：PNG 编码占 **97%**，而屏显根本不需要 PNG——需要的是 `ui.Image`（或 `RawImage` 直出）。按现契约每次翻页多付 100ms+ 与 400KB，200ms 预算被砍掉一半。

**选项**：A. 保持现签名，接受编码开销；B. 拆成两个方法——`Future<ui.Image> renderImage(int index, {required double maxEdgePx})`（屏显）+ `Future<Uint8List> renderPng(...)`（导出/OCR 裁图）。

**结论**：**选 B**，但属改 §7 签名，按 00-总览 §8 规矩须**先改 `项目具体规划formachine.md` 再改代码**，本轮不动代码，**待拍板授权**。

### 3.2 400% 缩放必须分块渲染

**根因**：`maxEdgePx = 页长 × 4` 只等于 **4 像素/pt**，而本机 400% 观感需 **4 × dpr = 10 像素/pt**。按 10 px/pt 整页渲染：

```text
595.3 × 10 = 5953 px 宽
841.9 × 10 = 8419 px 高
≈ 5000 万像素 ≈ 191 MB 位图/页
```

**结论**：一页即可打爆 4GB 设备。改为**按视口分块渲染 + 分块缓存（tile）**，不做整页高分辨率位图；实测单块 200×120pt 仅 4ms / 135KB，代价可接受。**须在 T1.5 前定案**，否则阅读器会写成 191MB 的炸弹。

### 3.3 pdfrx 不给字号，且片段粒度太碎

- `PdfPageTextFragment` 只有 `bounds`（`PdfRect`，**PDF 原生 y 向上**），**无 `fontSize`**。只能用片段高度近似：从分布看能清晰分出 5 档（10/11/12/13/29pt），近似可用，但它 ≠ 字号——多行片段高度会偏大。
- 片段是**碎**的：真实卷里 `"1"`（6×15.2）与 `"."` 分开、空片段 `""`、`"Synthetic"/"Exam"/"Paper"` 各自成片段，**题号 `1.` 会被切成两段**，直接对单片段跑 `^\s*(\d{1,3})\s*[.、．]` 会漏检（11/490 命中属碰巧有合并好的）。

**结论**：§6.1 的 L1 改为两步——① **先按 y 聚合行**（同一 y 带内片段按 x 排序拼成「行文本」）；② 再在行文本上跑题号正则与高度统计。层级判定用「**行内主字高跳变 ≥ 1.15x**」替代「字号跳变」，并接受它比真字号更易误判（长句/短句高度可差 1.15 倍）。

## 4. 结论与遗留

**结论**：T0.2 丢笔、压感、采样、掌拒、崩溃恢复全部达标，自建 canvas 方向成立；T0.4 首屏/翻页/400% 清晰度均以 60 倍以上余量通过，**PDF 库定为 pdfrx**。代价是 pdfium 6.4MB、需镜像补丁（阶段 0 应急）与三处契约修订。

**遗留（按优先级）**：

| 项 | 状态 | 需要什么 |
|---|---|---|
| 10 分钟连写 | 缺 | 连写 10 分钟不停，读 JSON 时间跨度判定 |
| 视觉延迟帧数 | 缺 | 手机 120fps 录像 5 段，数「笔尖接触 → 像素出现」帧差 ÷120 取中位 |
| 3000 笔内存 | 缺 | 连写至 HUD「页笔画」> 3000，记估算内存 + 截图 |
| §7 / §6.1 契约修订 | 待拍板 | 改 `项目具体规划formachine.md`（文档只读，需授权或用户自改） |
| pdfium 供应方式 | 待产品化 | T1.3/T1.5 前换内网镜像或随仓库分发 |
| T0.3 识别 spike | 下一步 | 手写中文短句 20 条，<70% 则改产品定位（最关键的 No-Go 数字） |

**调试期文件传输坑（记下来省下次时间）**：① `adb push` 到 `/sdcard/Android/data/<pkg>/files/` 能写，但目录由 shell 创建时应用读不了（`PathAccessException ... errno = 13`，scoped storage 按目录所有者判权限）；② `run-as pkg sh -c 'cat > file'` 被 SELinux 拒（`can't create ... Permission denied`），尽管目录属主就是应用；③ 可行写法是**写入由子进程完成**，不用 sh 重定向：

```bash
base64 paper.pdf | adb shell -T "run-as com.shuaqi.shuaqi sh -c 'base64 -d | dd of=/data/user/0/com.shuaqi.shuaqi/files/paper.pdf 2>/dev/null'"
adb exec-out run-as com.shuaqi.shuaqi base64 /data/.../files/x.png | tr -d '\r' | base64 -d > x.png   # 取回用 exec-out，adb shell 会加 CR 破坏 base64
```

产品走 `path_provider` + 应用自建目录，不会遇到。
