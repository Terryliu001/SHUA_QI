## 1. 书签圆角：三处一起改，缺一处还是"没做好"

用户的原话是"标签设计没有做好圆角处理（在列表、大图模式下都有这个问题）"。
拆开看是三个独立缺陷叠在一起：

1. **书签自身的角是直角**。卡片的圆角是 `ShqRadius.lg`（20dp），书签压在右上角，
   两枚直角尖会戳出卡片弧线之外 —— 放大截图里能明显看到"绿色方块戳在白色圆角外面"。
2. **书签贴着卡片顶边**（`top: 0`）。就算角是圆的，20dp 圆弧区域的切线仍然在往里收。
3. **大图卡的书签太宽**（74dp 上限 + 横向文字）。大图卡本身只有 ~230dp 宽，
   一枚宽书签直接压掉缩略图右上角，视觉上就是"贴了张便利贴"。

对应改法：

| 缺陷 | 改法 |
|---|---|
| 直角戳出圆弧 | `BookmarkClipper` 顶部两角改成半径 `kBookmarkRadius = 6` 的圆角（二次贝塞尔，不用 `arcToPoint`） |
| 贴边 | 两处 `Positioned` 都从 `top: 0` 改为 `top: ShqSpace.xs`，右侧保持 `ShqSpace.md` |
| 大图太宽 | `TagBookmark(vertical: true)`：文字**逐字换行**、宽度收窄到 `kBookmarkVerticalWidth = 21` |

竖排的取舍：标签上限 12 字，全竖排会比卡片还高 → 最多 `kBookmarkVerticalLines = 4` 行，
超出用省略号。拆字用 **runes** 而不是 `split('')`：后者遇到 emoji 会把代理对劈成两个孤立字符。

```dart
static String verticalText(String tag) =>
    <String>[for (final int rune in tag.runes) String.fromCharCode(rune)].join('\n');
```

## 2. 配色并入「编辑标签」：一个决定不做两遍

原设计是"编辑标签"+"标签颜色"两个入口（050 的做法）。用户否掉了：
标签在书架上**就是**一枚彩色书签，改名字和挑颜色是同一个决定。

- `showTagsDialog` 扩展为 `(initial, colors, onPickColor)`，对话框变成 Stateful：
  输入框每变一次就重算标签列表，色板跟着"正在打的这行"实时增减；
- 点色点**立即落盘**（`TagDao.setColor`），不等"保存"——用户能马上看到书签变色；
  文字部分仍走"保存"提交（避免打一半就被写进库）；
- 长按任意一枚书签 → 同一个弹窗（不再区分"具体是哪一枚"）；
- 卡片菜单删掉「标签颜色」项，`showWorkbookMenu` 去掉 `onEditTagColors`；
- 组件从 `bookshelf_page.dart` 的私有类提升到 `ui/bookshelf/tag_bookmark.dart`
  （`TagBookmarks` / `TagBookmark` / `BookmarkClipper` / `SwatchDot`）——
  卡片与弹窗共用一套，形状和配色不会长歪。

## 3. 大图卡的"统一感"：文件夹归属进元信息行

原来文件夹 chip 单独占一行，于是**有文件夹的卡比没文件夹的卡高一行**，
网格里看起来就是没对齐（用户说的"不统一"）。改成一个 `Row`：

- `页数 · 时间` 合成一段文本（`flex: 3`）—— 两个图标在窄卡上要吃掉 ~40dp；
- 文件夹 chip（`flex: 2`，`maxWidth` 取内容宽 45%）；
- 谁不够谁省略，**不让任何一方把对方挤没**。

顺带把 `_Meta` 的 `shrink` 参数删掉：大图卡已不再用它，留着是死参数。

## 4. 面板层级：多选 / 改卷 > 题面预览 = 收藏 / 对答案

`region_panel.dart` 的列顺序重排：

```
标题行
────────────
[多选] [改卷]              ← 常驻，最高
[多选时] 批量条
────────────
[选中时] 题面预览
         收藏 | 对答案      ← 同一块，同时出现
────────────
作答卡 / 题目列表 / 底部改卷条
```

判断依据是"**谁唤起了谁**"：多选 / 改卷是常驻能力（一直在），
题面预览与收藏 / 对答案是被同一件事（选中某题）唤起的 —— 后者本来就应该在一处，
而且都不该压在常驻能力上面。

## 5. 树视图：长按拖动改归属

`ShelfTree` 新增两个回调 `onMoveWorkbook(workbook, folderId)` / `onMoveFolder(folderId, parentId)`，
两者都给了才启用拖动（否则行为完全不变，可单测）。

- **载荷** `ShelfTreeDrag{id, label, isFolder, parentId, subtreeIds}`：只带 id 与名字，
  落库由外层做；文件夹额外带 `subtreeIds` 用于挡环。
- **三条硬规则**（`accepts`）：不能落到自己身上、不能落进自己的子孙、已经在里面就不动。
- **落点** = 文件夹行 + 「未分类」行。能拖动时「未分类」**恒显示**——它是唯一的"拖回顶层"落点。
- **拖动接管长按后，菜单必须有别的入口**：行尾加「更多操作」按钮（`IconButton` 仍用
  `shrinkWrap`，30dp 位置）。
- **落点自动展开**（`_revealFolder`）：不然拖完那卷就"消失"了（它其实进了折叠的文件夹）。
- **数据层再挡一次**：`_moveFolderTo` 用 `folderSubtreeIds` 复核，不信 UI 的挡法 ——
  `folder` 表一旦成环，之后任何一次遍历都会死循环。
- 高亮用每个落点自带的 `StatefulBuilder`：`onMove`（手指进入范围）就亮，
  比等 `candidate`（数据命中判定完成）早半拍。

## 6. 真机踩坑：`adb input swipe` 拖不动

`input swipe X1 Y1 X2 Y2 1500` 看着像"慢慢拖"，实际是**只发 DOWN / 两个 MOVE / UP**，
中间没时间给长按判定。第一次验证时树里毫无反应，误以为是代码问题。

正确做法是**分步发事件**（同一 `sh` 里用 `;` 串起来，保证同一个进程发）：

```bash
adb shell "input motionevent DOWN 700 620; sleep 1.2; input motionevent MOVE 700 640; \
  sleep 0.3; input motionevent MOVE 700 500; sleep 0.3; input motionevent MOVE 700 430; sleep 0.5"
# 截图看浮起小条与落点高亮
adb shell input motionevent UP 700 430
```

另一个观察：**文件夹行左端的展开箭头/图标区域**长按能起拖，`group` 名字附近
在部分坐标下没有起拖（行内有多层手势竞争）。这不是缺陷——用户会按住行本身——但
验证时优先按图标或行左侧。
