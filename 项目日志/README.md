## 2. 两类日志与命名（压缩后仍适用）

| 类型 | 文件名 | 用途 | 写法 |
|---|---|---|---|
| **事件日志** | `NNN-YYYY-MM-DD-主题.md` | 每次实质性会话一篇 | 追加式；写完不再改历史结论，有新结论新写一篇并指向旧篇 |
| **阶段日志** | `阶段N-名称.md` | 一个阶段的进度与验收 | 当前未单独建，进度汇总在本 README §5 |

命名规则：
- `NNN` 三位数字，全局递增，不复用、不补号；**合卷沿用其首篇编号**（如 004 合卷以原 005/006 为主，编号取 004 段位）。
- 日期为实际发生日（本地时区 GMT+8）。
- 主题用中文短语，能一眼看出这篇在讲什么。

## 3. 每篇必带的头部

```markdown
| 项 | 值 |
|---|---|
| 日期 | YYYY-MM-DD |
| 阶段 / 任务块 | 阶段N / T-x.y |
| 本轮范围 | 一句话写清做了什么、**明确没做什么** |
| 结论 | 通过 / 部分通过 / 阻塞 |
```

## 4. 硬规矩

1. **只写事实与可复现的结论**；没实测就标「未验证」，不写「应该没问题」。
2. **命令与输出留证**：贴关键命令与关键行，不贴整屏日志。
3. **数值带单位与口径**：≤200ms 要说明设备与模式；debug 数据标「无参考价值」。
4. **未决问题单列**，写清「选项 / 倾向 / 需要谁拍板」。
5. **不记录敏感信息**：API Key、设备序列号以外的个人信息。
6. **数据契约优先**：SIF/表结构/颜色索引这类格式变更，先定版再落盘。
7. **压缩不删根因**：合卷可以删过程、删重复背景，但「现象 → 根因 → 修法 → 证据」必须完整。
